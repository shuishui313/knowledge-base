**AI-19**

## 面试在问什么

物业报修助手已经能按权限检索，常见通告也做了语义缓存。上线之后，投诉常常不是「搜得不够像」，而是「不该翻手册的问题，去翻了手册」。有人问「WO-3184 师傅到了没？」，助手根据一份旧 FAQ 说「一般两小时内」，工单系统里其实已经改约。有人只说「我的单到边了？」，没有工单号，系统仍去检索通告。还有人一句里既要报漏水、又要查进度，助手只答了其中一半。

面试官很少停在「我们接了 RAG」。他们接着问：什么问题根本不该进知识库？只靠关键词够不够？不确定时能不能默默走检索？这和换模型、改写问法是不是一回事？

只说「有工单号就查系统，其他都丢给 RAG」，偏弱。能讲清查询路由是先选路再做事、硬规则和模型分类各管什么、不确定时不要默认检索、路由准确率和回答质量要分开验收，才像 FDE。

[语义缓存](AI-18-语义缓存(Semantic-Caching).md) 已经提过：实时和个人问题不要拿来共用。[权限感知检索](AI-17-权限感知检索(Permission-aware-Retrieval).md) 管的是「能不能看见」。这篇写更前面的一层：这个问题该走哪条路。

公开面经里的常见问法就围着这几件转：手册问答和业务系统怎么分流，路由失败怎么发现，不确定时怎么办，以及和模型路由、查询改写差在哪。

## 定义

查询路由（Query Routing，也常叫意图路由 / Intent Routing）：先判断这条问题该走哪条路径，再去做检索、查系统、读缓存、转人工或拒答。它决定的是「去哪里办」，不是「这句话怎么改写才更好搜」，也不是「用哪一个生成模型」。

路径可以是不同的资料库、不同的业务系统、一条固定流程、转人工，或直接说明做不到。选定之后，这一路里仍可能用工具去查系统，见 [工具调用](AI-03-工具调用(Tool-Calling).md)。

和另外两件常被混在一起的事要分开：

| 做法 | 决定什么 | 不是什么 |
|------|----------|----------|
| 查询路由 | 这条问题走哪条路径 | 不负责把口语改写成书面检索词 |
| [查询改写](AI-21-查询改写(Query-Rewriting).md) | 在已经选定的检索路上，把问法变得更好找 | 不决定该不该查工单系统 |
| 模型路由 | 这一步用哪一个模型（便宜的、推理的、本地的） | 不决定答案该来自手册还是业务系统 |

三者可以同时存在。先选路，再按需要改写或选模型。把「换一个更大的模型」当成路由，解决不了问错路的问题。

## 一次请求里实际发生了什么

1. 先看有没有硬信号。工单号、明确的「我的单 / 我的预约」、登录后才能看的个人进度，走规则即可，不必先问生成模型。规则要写清楚：有单号就查系统；没有单号但在问自己的进度，先补身份或请对方给单号，不要去翻手册。
2. 硬规则没卡住，再用分类。常见有两种。逻辑路由：把可选路径写成封闭集合，让模型以结构化输出选出一条，见 [结构化输出](AI-11-结构化输出(Structured-Output).md)。语义路由：把问题和各条路径的描述做成向量，按相似度选最近的一条。路径集合要闭合，不要让模型发明一条不存在的路。
3. 看把握。规则命中就走规则；模型或相似度低于阈值，不要默默丢进检索增强生成，见 [检索增强生成](AI-02-RAG检索增强生成(RAG).md)。该问一句澄清、转人工，或说明手册和系统都办不了，见 [人工在环](AI-15-人工在环(Human-in-the-Loop).md)。
4. 上路之后，这一路自己的约束仍在。手册检索仍要权限和版本；只有确定是可共用的通告问答，才考虑语义缓存；查系统要用登录身份，而不是把上一路的缓存答案拿过来。
5. 把选择记下：走了哪条路、是规则还是模型决定的、当时有没有把握。事后才能分清「答错是因为路选错了，还是路对了但检索或生成坏了」，见 [可观测性](AI-16-可观测性(Observability).md) 和 [评测](AI-05-评测(Evaluation).md)。

一条问题里有两个意图时，不要硬塞进一条路。例如「厕所漏水，顺便问 WO-3184 到了没？」应当拆开，或先问清楚先办哪一件。偷偷只走其中一路，用户会以为另一件也查过了。

## 会在哪里坏

常见不是「没做路由」，而是默认路选错了，还把它当成检索或模型的问题来修。

- **什么都丢给 RAG。** 手册里有一句「一般两小时内」，问工单进度时就会被旧 FAQ 接住。演示书面题能过，不代表路由过了。
- **只靠关键词。** 「WO-」开头当工单，对方写成「工单 3184」或「师傅到咗未」就会漏。反过来，手册问法里偶尔出现「工单」两个字，就被送去查系统，系统里又没有这个号。
- **不确定时默认检索。** 分类没把握，仍走进知识库，看起来像在回答，其实是在不该翻的资料里找句子。低把握要澄清、转人工或拒答，不要用检索来赌。
- **多意图只走一路。** 一句里既报修又查进度，只答了手册步骤，进度其实没查。
- **把模型路由当成查询路由。** 换了更大的模型，问错的路还是错的。
- **路由本身没有验收。** 只看最终答得像不像。路错了，后面的召回率再好看，也是在错的库里量。要把「必须走系统」「必须走手册」「必须拒答或转人工」做成冻结集，单独看路由准确率。

## 香港落地例子

继续那间虚构的沙田私人屋苑助手。数字和户号都是编的，不代表任何机构。

先把路分成几类，不要共用一个入口就结束。

查进度、改约、师傅是否出发：走工单系统，按登录身份查。问题里有「WO-3184」，或住户已登录并在问「我的单」，都走这条。不要进手册，也不要进语义缓存。

怎么处理渗漏、今晚停不停水、怎样申请临时通行证：走现行手册或通告的检索。这一路才谈混合检索、[查询改写](AI-21-查询改写(Query-Rewriting).md)和缓存。

「我可不可以关大厦总阀」这类有安全风险、或手册明确说转管理处的：不要只生成一段安慰，该按规则转人工，或给出明确指引后停。

手册和系统都办不了的，例如问邻居单位的工单：拒答。不是检索分低，就换一种说法再搜一遍。

前台同事说「加多几个关键词就够」。不够。住户会说「师傅到咗未」，不一定带单号；也会在同一句里先讲漏水再问进度。规则先接住单号和「我的单」，其余用封闭的路径列表做分类；低把握就问一句「你是想查工单进度，还是想看渗漏怎么处理？」，而不是默认翻手册。

验收时，冻结集里至少要有：带单号的进度题、不带单号的「我的单」、纯手册口语题、手册里没有应拒答的题，以及一句双意图的话。只拿「厕所地台渗水，我先可以做什么？」做演示，看不出路由有没有坏。

四类雇主的差异（对照即可）：

| 雇主类型 | 这件事上的侧重点 |
|----------|------------------|
| AI 原生 / 产品公司 | 路径列表、规则和冻结集是带版本的产品配置；改分类模型前，先看走错路的题有没有回归 |
| 大厂云与平台 | 托管知识库若默认全部进检索，要能配置分流，并在追踪里看到走了哪条路、是规则还是模型决定的 |
| 咨询与系统集成 | 把分流规则、低把握时的动作和路由验收写进范围；工时往往花在理清「什么不该进知识库」，而不是调检索 |
| 甲方企业内部（如银行、保险、地产） | 进度和客户资料必须走系统；错路可能把旧 FAQ 或别人的进度说出去，路由记录本身也可能被问到 |

## 面试怎么说

> "Query routing means we decide which path a question should take before we retrieve or generate. 'Where is WO-3184?' goes to the ticket system with the caller's identity, not to a handbook or an old FAQ. 'What should I do about a leak?' can go to the current handbook. Routing is not query rewriting — rewriting only helps retrieval after the path is already chosen — and it is not model routing, which only picks which model to call. Hard signals like a ticket ID or 'where's my order' should be handled by rules, not by hoping an LLM notices. For the rest, I use a closed set of routes, either with structured output or by comparing the question to route descriptions. If confidence is low, I clarify, hand off, or refuse; I do not silently default to RAG. We evaluate routing on a frozen set that includes must-go-to-system, must-go-to-handbook, must-refuse, and two-intent questions. Answer quality on written handbook demos can look fine while routing is already wrong."

先把「选路」和「检索、改写、换模型」拆开，再说硬规则管什么、不确定时不要默认检索、路由要单独验收；用客户习惯的语言（粤语或普通话）讲清楚，用英文把结论写下来。

## 小练习

仍是上面那间虚构的屋苑助手。同事报了三句「我们已经做了路由」。哪一句其实是查询改写？哪一句是模型路由？哪一句会把进度题送进旧 FAQ？各用一句话。

1. 所有问题先做成向量，和「手册问答」这条描述一比，超过阈值就检索；没设其他路径，「WO-3184 师傅到了没？」也去翻 FAQ。
2. 口语问法会先改写成书面检索词，再在同一套手册索引里搜。工单进度题改写完仍然走手册。
3. 网关按题目难度挑选生成模型，简单通告用小模型，复杂解释用推理模型。进度题若被当成手册题，仍不会去查工单系统。

### 小练习

1. **会把进度题送进旧 FAQ。** 只有「手册问答」一条路，相似度再怎么比，也只是在手册里找。进度题被接住，不是检索阈值的问题，是根本没把「查系统」设成一条路。

3. **其实是模型路由。** 它只决定用哪一个生成模型。路选错了，换更大的模型也不会去查系统。

### 自测 1

差别：查询路由决定这条问题走手册、工单系统、转人工还是拒答。查询改写是在已经选定的检索路上，把问法变得更好找。模型路由是这一步用哪一个模型。先选路，再按需要改写或选模型。

没有单号，不等于该去翻手册。「我的单到边了？」答案只属于这一户、这一刻，应补身份或请对方给单号，再查系统。默认交给 RAG，旧 FAQ 里的「一般两小时内」就会冒出来，而且还可能看起来像引用。

验收不能只看手册书面题答得像不像。冻结集里要有：必须走系统的题（带单号、以及不带单号的「我的单」）、必须走手册的口语题、必须拒答或转人工的题、以及一句双意图的话。路由准确率和后面的检索、生成质量分开看。路错了，召回率再好看也是在错的库里量。

### 自测 2

可以走产品说明检索的：某个产品当前版本的转账上限、公开的操作步骤。这一路仍要带条款或产品版本，条款一改，旧答案不能继续用。

必须走核心系统、按客户号查的：已出结单、余额、最近一笔转账是否到账。这些和屋苑里的「我的工单」是同一类：句子可以完全一样，答案不能从手册或别人的缓存里取。

不确定时不能默认检索。客户说「我那笔钱呢」却没有足够信息时，应澄清是查到账、查限额，还是查操作方法。若默默走进产品说明，可能用一段限额解释去回答一笔未到账的转账，听起来像有依据，其实问错了路。低把握就问一句或转人工，不要用检索来赌。改完用银行这类题重跑冻结集，不要只用屋苑停水通告的例子交差。

## 一句话总结

> **查询路由是：先决定这个问题走哪条路，再检索、查系统、转人工或拒答。** 默认交给 RAG，就是最常见的选错路。规则先接住硬信号，模型分类要用封闭路径，没把握就停下来问；路由准确率和回答质量要分开验收。
