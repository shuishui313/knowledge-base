**AI-24**

## 面试在问什么

物业报修助手已经会混合检索、重排和引用。可如果手册在入库时被切坏了，后面的检索再认真，对的内容也进不了候选，或者进来的只是半条规则。

住户问「地台漏水我先关总掣得唔得」。规程第 1 条写「先关闭相关阀门」，紧跟着的例外写「不要关闭大厦总阀」。按固定字数一切，这两句分到两块。向量只找回了前半句，模型就给出危险建议。另一次，收费表被切到一半：块里只有「临时通行证按金」，下一栏的金额和「业主免收」落在另一块。还有一次，团队把切块从 500 字改成 200 字，却没有重建索引，线上检索的仍是旧块。

面试官很少停在「我们按 512 个 token 切，并加了重叠」。公开面经里的常见问法围着这几件转：为什么不能只按字数切？规则和例外为什么必须留在同一块，或至少有重叠？表格和条款号怎么处理？改了切法为什么要重建索引？这一层要怎样验收？

只说「切小一点效果更好」，偏弱。能讲清切块决定的是检索和引用的单位、固定长度只是起点、结构切块要保住完整条款和表格、元数据要跟着块走、改切法必须重建并用冻结集回归，才像 FDE。

[检索增强生成](AI-02-RAG检索增强生成(RAG).md) 是整条链路。[嵌入与向量检索](AI-08-嵌入与向量检索(Embedding).md) 讲向量怎么表示一块。[混合检索](AI-23-混合检索(Hybrid-Search).md) 和 [重排序](AI-22-重排序(Reranking).md) 都假设块已经切好。[引用与溯源](AI-20-引用与溯源(Grounding-and-Citation).md) 核对的也是这些块。短课里的全流程见 [FDE-20](../hk-fde/FDE-20-2026-11-22-LLM应用-RAG全流程切块召回重排引用.md)。本篇只写入库时怎么把文档变成可检索、可引用的块。

## 定义

文档切块（Chunking）：在建立索引时，把一份文档切成较小的片段，每个片段作为检索和引用的单位。它改的是「库里有哪些可被找到的证据」，不是查询到来时再把文档临时切开，也不是重排或生成。

| 做法 | 决定什么 | 不是什么 |
|------|----------|----------|
| 固定长度切块 | 按字数或 token 数切开，常加一段重叠，避免句子刚好落在边界 | 不是按条款或表格的完整意义来切 |
| 按结构切块 | 按标题、条款、段落、表格等文档边界来切，尽量让一条规则连同例外、一张表连同行头成为一块 | 不是可以不做长度上限；过长的章节仍要再切 |
| 父子切块（small-to-big） | 用较小的子块做检索，命中后再把父段（整条规程或整节）交给生成 | 不是把整本手册塞进窗口 |
| 语义切块 | 按句子之间意思是否转折来决定切点 | 不是默认更优；换嵌入模型时往往要重切，并在冻结集上比较 |

块太小，一条完整规定被拆开，检索到的证据不自足，引用也对不上一句完整的话。块太大，一段里混了几件事，向量被稀释，进了提示词也容易让模型错过中间那条例外。重叠可以补边界上被切断的句子，但会制造近似重复的块，不能代替按结构来切。

每一块还要带上标题路径、来源、生效版本和权限标签。引用时才能说清出处，过滤时才知道这块能不能给当前用户看。换切法、换解析或换嵌入模型，都要重建索引，见 [嵌入与向量检索](AI-08-嵌入与向量检索(Embedding).md)。

## 一次索引（和一次提问）里实际发生了什么

1. 先解析。把 PDF、扫描件、表格变成仍带结构的文本。解析坏了，后面怎么切都救不回一张被打乱的收费表。
2. 按结构切：一条规程连同「但是」「若」后的例外尽量留在同一块；一张表连表头成为一块；条款号不要和正文拆开。章节过长时，再在结构内部做有重叠的切分。
3. 给每块写上标题路径、页码或条款号、版本、权限。这些字段要随块进入索引，不能只存在原文件里。
4. 需要时做父子索引：子块用于召回，父块用于生成。检索到「不要关闭大厦总阀」这一句时，生成应能看到完整的应急步骤。
5. 用与查询相同的嵌入模型为块建立向量索引，并建立关键词索引，见 [混合检索](AI-23-混合检索(Hybrid-Search).md)。
6. 提问到来时，检索的是这些已经切好的块。重排、生成和引用都不能补回入库时被切丢的上下文，见 [重排序](AI-22-重排序(Reranking).md) 和 [引用与溯源](AI-20-引用与溯源(Grounding-and-Citation).md)。
7. 记下切块规则的版本、解析方式和每块的标题路径。答错时才能分清是切坏了、召回没找到，还是生成没用上，见 [可观测性](AI-16-可观测性(Observability).md) 和 [评测](AI-05-评测(Evaluation).md)。

## 会在哪里坏

常见不是「没有切块」，而是按字数一切就上线，再把后面的失败算到模型头上。

- **只按固定字数切。** 规则和例外被切开，表格被切到一半，条款号落在上一块。重叠只能补边界，补不回结构。
- **块过大。** 一节里混了几个主题，向量变模糊；即使召回了，模型也可能略过中间的例外。
- **块过小、又不做父子扩展。** 检索很准，但生成只看到半句话，引用也对不完整。
- **元数据没跟着走。** 块上没有标题路径或版本，引用只能说「手册里写过」，过滤也无法按屋苑或生效版本做。
- **改了切法却不重建。** 线上仍在检索旧块。切法、解析、嵌入模型都是索引的一部分，改了就要重建并回归。
- **解析先坏了。** 双栏 PDF、页眉页脚、扫描件被读成乱序，切块只是把乱序再切一刀。
- **验收只用书面标准题。** 问法和标题几乎一样，看不出例外是否被切开、收费表是否完整。冻结集里要有：必须看到完整条款才能答对的题、表格题，以及边界上那句例外。

## 香港落地例子

继续那间虚构的沙田私人屋苑助手。数字、户号和通告编号都是编的，不代表任何机构。

手册「渗漏应急」第 1 条写「先关闭相关阀门」，紧接着写「不要关闭大厦总阀，否则可能影响消防供水」。按 200 个字一刀切，这两句分到两块。住户问能不能关总掣，检索只带回前半句。正确做法是：这条规程和例外留在同一块；若章节必须再切，中间留重叠，并做父子索引，命中任一句都把整条规程交给生成。块上带着「渗漏应急 / 现行版」这条路径。

收费表「访客临时通行证」一行是「住户 HKD 200，业主免收」。如果按金和免收条件被切到两块，向量可能只找回「按金 200」，模型就漏掉业主免收。表格应连表头整行成为一块，不要按单元格或固定宽度横切。

中英对照通告不要把一句中文和它的英文翻译拆进两块后，又把它们当成互不相关的证据。可以按语种分块，但要共享同一标题路径和版本；验收时粤语问法和英文条款都要能回到同一条现行规定。

验收时，冻结集里至少要有：必须连同例外才能答对的题（关总阀）；必须看到完整一行收费才能答对的题；只命中半块就应当拒答或转人工、不能给危险建议的题。只拿「按金是多少」的标准书面题做演示，看不出切块有没有坏。

四类雇主的差异（对照即可）：

| 雇主类型 | 这件事上的侧重点 |
|----------|------------------|
| AI 原生 / 产品公司 | 切块规则是带版本的链路配置；改长度、重叠、结构规则或父子策略前，要用「例外被切开就答错」和「表格必须整行召回」的冻结集做回归 |
| 大厂云与平台 | 托管知识库要能讲清切块发生在哪一层、客户能否按条款或表格定制，以及改切法后能否重建并在追踪里看到块的标题路径 |
| 咨询与系统集成 | 把「按结构切、规则与例外同块、表格整行、元数据随块、改切法必重建」写进范围；工时往往花在解析和切法，而不是换一个更贵的模型 |
| 甲方企业内部（如银行、保险、地产） | 条款和费率表必须作为完整证据被召回；原文不出未经批准的环境；切法变更要能重建索引，并用条款号题、例外题和「资料里没有」的题验收 |

## 拓展补充

有一种常见补法，是在嵌入之前给块补上标题路径或一小段文档上下文，让向量自己带一点「这块属于哪一节」（有人把这类做法叫做 Contextual Retrieval）。它能减轻「块本身看不出所属章节」的问题，但不能代替「规则和例外留在同一块」，也不是可以不做重建：改了补全模板，同样要重做索引，并在冻结集上比较。

## 面试怎么说

> "Chunking is an index-time decision: it sets the unit we can retrieve and the unit we can cite. I don't start with a raw token window. I chunk by document structure so a rule and the exception that follows it stay together, and a fee table stays with its header and the full row. Every chunk carries a heading path, version, and permission tag. If a section is still too long, I split inside it with a little overlap, and I often retrieve a small child chunk then expand to the parent clause for generation. Overlap only patches a sentence cut at the boundary; it won't repair a table split in half. When we change the chunking rules, the parser, or the embedding model, we rebuild the index. We evaluate on a frozen set with questions that fail if the exception was split off, and questions that need a complete table row — not just the tidy written examples."

先把「入库时决定检索和引用的单位」说清楚，再强调按结构切、元数据随块走、改切法要重建；用客户习惯的语言（粤语或普通话）讲清楚，用英文把结论写下来。

## 小练习

仍是上面那间虚构的屋苑助手。同事报了三句「我们已经重新切过块了」。哪一句仍然会把例外切开？哪一句改了切法却没有生效？哪一句才是正确处理？各用一句话。

1. 团队按固定 200 字切手册，只加了很小的重叠。住户问能不能关总掣时，检索只带回「先关闭相关阀门」，「不要关闭大厦总阀」在下一块。没有按条款切，也没有父子扩展。
2. 团队把切法改成按条款切，规则和例外会留在同一块，但没有重建索引。线上检索的仍是按固定字数切好的旧块。
3. 按结构把规程和例外留在同一块，收费表整行带表头，块上有标题路径和版本。改切法后重建了索引，并用「关总阀」和收费表题做了回归。

1. 这间屋苑。文档切块决定的是什么，它和重排有什么不同？为什么不能只按固定字数切？重叠能解决什么、不能解决什么？改了切法为什么必须重建索引？这一层要怎样验收？
2. 如果面试官来自虚拟银行，客户助手要回答冷静期可否取消、某条条款号是什么意思，以及某张费率表里「优惠不适用于企业客户」这一行。和这间屋苑相比，哪些材料必须作为完整证据被切在一起？切坏了会有什么后果？为什么不能只拿书面标准题验收？

### 小练习

1. **仍然会把例外切开。** 很小的重叠补不回一条被固定长度切断的例外。应按条款把规则和例外留在同一块，必要时再做父子扩展。

3. **正确处理。** 结构切块保住了完整证据，元数据随块走，并且重建后用「半块就答错」的题做了回归。

### 自测 1

切块决定的是入库之后，检索和引用的单位是什么：库里有哪些可被找到的证据。它发生在建立索引时，不是查询到来时再切一次。重排只在已经召回的候选里决定留下谁，补不回入库时被切丢的上下文。

不能只按固定字数切，是因为条款、例外和表格的边界很少刚好落在某个 token 数上。规则和例外被切开，或收费表被切到一半，检索到的就不是一条完整证据。

重叠能补边界上被切断的句子，但不能代替按结构来切，还会制造近似重复的块。表格被横切、例外被分到下一块，加重叠常常救不回来。

改了切法必须重建索引，是因为线上检索的是已经写进库里的旧块。解析方式和嵌入模型同样是索引的一部分，改了也要重建，再用冻结集回归。

验收不要只用最终答案好不好看，更不要只用书面标准题。冻结集里要有：必须连同例外才能答对的题、必须看到完整一行表格才能答对的题，以及只命中半块就应当拒答或转人工的题。还要能从追踪里看到这块的标题路径和切块规则版本。

### 自测 2

和屋苑里的「不要关闭大厦总阀」、收费表整行同类、必须作为完整证据被切在一起的：冷静期条款和它的例外或限制条件，费率表里「优惠不适用于企业客户」这一整行连同表头，以及客户报出的那条条款号和它的正文。这些材料若被固定字数切开，助手可能只看到可以取消或看到优惠金额，漏掉限制条件，给出不符合现行条款的答复。

实时账户余额、某笔转账到了没有，仍然要查核心系统，不靠把说明书切得更细来补。

只拿书面标准题验收，会漏掉真实失败：例外落在下一块、表格被横切、中英条款对不回同一版本。改完要用银行这类题重跑冻结集，不要只用屋苑关总阀的例子交差。

## 一句话总结

> **切块是在入库时决定检索和引用的单位。** 按结构来切，让一条规则连同例外、一张表连同行头成为一块；元数据跟着走。固定长度和重叠只是起点。改了切法必须重建索引，并用「半块就答错」的题验收。
