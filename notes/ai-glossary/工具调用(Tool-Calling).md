## 一、定义

工具调用（Tool Calling），也常叫函数调用（Function Calling）= 模型在需要外部事实或动作时，不直接把答案写完，而是先发出一份结构化请求：要调用的名字，加上参数。真正查库、调接口、做计算的是你的程序。程序把结果交回，模型再决定继续调用，或写给用户的那句话。

请求本身什么都没做。模型输出一个函数名和保单号，理赔系统里的状态不会因此改变，也不会自动出现在回答里。中间必须有一段你控制的执行。少了这一段，对话里只有一份「打算去查」的 JSON。

和纯文本生成比，差别在依据从哪来。纯生成只使用训练时形成的参数记忆，以及你贴进对话的文字。工具调用把「此刻某系统里的字段」或「一次算完的数字」接进同一段对话。模型仍然负责听懂问题和组织句子。它不再被当成那个系统本身。

和 RAG 的差别在谁决定去取什么。本系列的 [RAG 检索增强生成（RAG）](RAG检索增强生成(RAG).md) 是一条固定顺序：先检索，把片段放进上下文，再生成。检索通常在模型开口之前就做完了。工具调用把「要不要查、查哪一个、参数是什么」交给模型。检索可以包成其中一个工具，于是两条路叠在一起：模型决定调用资料检索，工具背后仍是切块、检索、把片段交回。进度、余额、下单不是文档片段，不该装进 RAG 来冒充。

| 做法 | 回答依据 | 典型失败 |
|------|----------|----------|
| 纯生成 | 参数记忆，加上对话里已经写明的字 | 编一个像进度的状态、像条款的数字 |
| RAG | 检索到的片段，加上模型的语言能力 | 片段找错，于是带着章节号答错 |
| 工具调用 | 某次真实执行的返回，加上模型的编排 | 没执行却说查过了；执行失败仍把话说满 |

三行可以同时出现在一个产品里。客户问「这单到哪了，这类事故赔不赔」：进度走事务接口，条款走资料。模型的工作是分开这两问，而不是用一个更顺的句子把它们糊成一句。

## 二、为何需要

参数记忆停在训练结束的那天。昨夜的批量、今早改过的费率、这一刻的理赔队列，都不在权重里。把它们再训练进去，也只是把「过期」推迟到下一次训练。会变的状态不该靠背。

私有系统本来就不是公开文本。保单、工单、柜面权限在你们的接口后面。把库导出塞进训练集，既过时，也不该发生。模型需要的是一次受权限约束的读取，不是一份它永久记住的副本。

有些事是副作用。下单、写工单、发通知，是世界被改了。生成一句「已经帮您提交」不会产生工单号。工单号来自那个真的写入并返回编号的系统。调用请求只是提议；执行成功的回执才是提交。

还有一类是确定性计算。两日期间隔、税额、汇率换算，规则是死的。语言模型会把算式说得很顺，数字仍然可能错。这种错和「不知道进度」不同：它不是缺资料，是把不该交给抽样的步骤交给了抽样。计算器、数据库里的公式、业务系统里已经写好的核算，比再提示一次「请仔细计算」可靠。

所以分工是稳定的：模型擅长把人话收成步骤，不擅长代表此刻真实世界的状态。编排靠模型。状态、金额和是否已经写入，靠工具的返回。

它不因此什么都能做。工具清单里没有的能力，模型不应该用一句更自信的话补上。清单里有、但这句话不该用的工具，也不该为了显得查过而硬调一次。

四件事可以对照着看，决定该不该做工具，而不是先选一个模型：

| 需求 | 只靠生成时会怎样 | 工具该交回什么 |
|------|------------------|----------------|
| 会过期的事实 | 用训练截止日前的常见说法填空 | 这次查询得到的字段，带时间 |
| 私有系统里的记录 | 编一个像内部编号的字符串 | 在调用者权限内读到的那一行 |
| 写入、通知、下单 | 用完成时说出「已经办好」 | 系统返回的回执；没有回执就还没办 |
| 按规则算死的数 | 算式顺、得数错 | 计算器或业务公式的输出 |

## 三、进展与常见形态

2023 年，OpenAI 在对话接口里加入 function calling：开发者声明若干函数，模型可以返回函数名和一份 JSON 参数，由应用执行。随后这套声明收成 tools。一次回复里可以带多个调用；也可以指定这次必须调用、不许调用、或只能调用其中某一个。Anthropic 在 Messages API 里提供 tool use，同样是名字、说明和一份参数结构，模型返回工具调用，应用把结果交回。其他厂商的名字不同，骨架相近：用 JSON Schema 描述参数，让模型在「说话」和「发出调用」之间选择。

Schema 先解决的是形状。保单号是字符串还是数字、哪些字段必填、状态只能取哪几个值，可以在解码时就卡住。早期更多是请模型按这个 JSON 来，括号和类型仍会坏。后来多家加上更严的约束解码：OpenAI 文档里的 strict tools / Structured Outputs 属于这一类；Anthropic 的 tool use 也会按输入的 JSON Schema 校验。格式错误会少很多。形状正确不等于事情正确。Schema 证明不了这个保单号存在，也证明不了当前柜员可以看。

一次提问里的循环大致是这样：

```
可用工具清单 + 对话
        ↓
模型：零个或多个调用请求（名字 + 参数）
        ↓
应用：校验 → 执行或拒绝 → 结果或错误原文
        ↓
结果追加进对话，再交给模型
        ↓
模型：再调用，或写出给用户的话
        ↑__________________________|
```

有先后的步骤必须分轮。先取保单号、再用保单号取进度，第二步的参数来自第一步的返回，不能在同一次回复里猜。彼此独立的查询可以并行：同时问两张保单的进度，一次回复里两个调用即可。并行省的是来回，不省规则。两个写入并行，如果没有幂等，会做两次。

轮数要有上限。模型可能反复改一个过不了校验的参数，或者在两个只读工具之间来回。上限到了，就停下来说明「还没有可用的结果」，而不是再让它自由发挥一段看起来像结论的话。

有人把「模型 + 工具 + 循环」叫做 Agent。更紧的说法是：Agent 还带着一个还没完成的目标、一个停的条件，以及跨步骤还在的状态。单次查进度再回答，是工具调用，不必叫 Agent。研究里常被一起提到的 ReAct（Yao 等人，ICLR 2023）讲的是把推理和行动交错进行：先想一步，做一个动作，看观察，再想。工具循环是这个想法在接口里的一种落地。名字叫大了无害。把「会循环」理解成「可以自己改生产数据」就有害。循环里的每一步权限，仍是那个工具的权限。

失败要看得见。下面几种在联调时都常见，而且都会被一段流畅的中文盖住：

| 你看到的 | 实际发生了什么 | 回答不该怎样 |
|----------|----------------|--------------|
| 参数校验失败 | 缺字段、类型不对，或取值超出 Schema | 不要悄悄改成一个差不多的参数再执行 |
| 工具超时或 5xx | 系统没有给出这次的状态 | 不要用「这类一般在审核中」填上 |
| 只有自然语言 | 模型说查过了，对话里没有调用 | 把这句话当成未核实，而不是当成结果 |
| 调用了，答案却没用上 | 返回在上下文里，句子仍来自记忆 | 状态、编号、日期要能指回这一次返回 |
| 同一写入出现两次 | 重试或并行没有幂等键 | 两次都当真执行，就会重复下单或重复开单 |

第三行尤其容易漏。产品如果只展示模型最后说的话，用户无法区分「执行过」和「演了一段执行过」。调用名、参数、耗时、错误原文要留在日志里。对用户至少不能把失败说成成功。

还有一种静默失败出在应用，不出在模型：工具报错了，程序丢掉错误，改把一句「请根据常识回答」送回去。模型于是用参数记忆把进度补完。日志里看得到一次调用，答案却不是那次调用的结果。交回的内容必须是结果或错误原文，不能是你替它圆上的成功。

## 四、缓解与落地做法

工具描述是模型唯一能读到的说明书。名字要像动作，不要像内部项目代号。写清三件事：何时用、每个参数的含义、何时禁止。禁止场景和适用场景同样有用。没写「不要用它改状态」，模型就可能把「帮客户催一下」收成对只读接口的调用，或者反过来，把进度问题收成一次写入。

描述要短，短在决策边界上，不是短到只留一个动词。整本操作手册塞进描述，模型会抓不住「这句该不该调」。手册放在资料库或另一个检索工具里。描述只回答：现在这句人话，该不该用我。

参数用 JSON Schema 限制类型和必填项。服务端再做业务校验，并且不信任模型抄来的参数。对话里出现了保单号，只说明模型会抄写，不说明这位柜员或这位客户有权查看。存在性、归属、权限在你的接口里判断。校验失败就把失败交回，不要为了让对话继续而替换成邻近的另一个号码。

超时、重试、幂等分开写。读接口可以短超时、有限重试。写接口先要幂等键：同一次申请的重试返回第一次的回执，而不是再写一笔。重试耗尽就把超时或错误原文作为工具结果交回模型，并禁止应用层编一份成功。模型会把你藏起来的空缺用很顺的中文补完。把原文给它，它才有机会说这次没有查到。

可以先把描述写成一张小卡片，再去调模型：

```
名称：get_claim_status
做什么：按保单号读取理赔进度。只读，不修改任何状态。
何时用：用户在问对话里已经出现的某一张保单到哪一步。
何时不用：解释保障范围、估算应赔金额、催办或改状态；保单号还没出现。
参数：policy_id，字符串，必填。只接受保单号，不要用客户姓名去猜一张保单。
失败时：你会收到错误原文。返回里没有 status，就不要报告进度。
```

### 一个柜面例子

虚拟的香港保险公司柜面。客户问：「保单 P-18442 这单理赔到哪了？」同事把这句话交给助手。助手只有上面那个只读工具，凭证是这位柜员自己的权限，不是一把全库钥匙。

模型返回的请求是：

```json
{"name": "get_claim_status", "arguments": {"policy_id": "P-18442"}}
```

到这一步还没有进度。程序核对：号码格式符合 Schema，这张保单在该柜员可查的范围里，然后调用内部理赔接口。

接口返回：

```json
{
  "policy_id": "P-18442",
  "claim_id": "CLM-90211",
  "status": "waiting_documents",
  "missing": ["医疗收据正本"],
  "updated_at": "2026-11-04"
}
```

给客户的话只能来自这些字段：「这单在等医疗收据正本，索赔编号 CLM-90211，进度更新于 2026-11-04。」不附加「所以这周一定能批」。接口没说批复日期。

若接口超时，交回模型的工具结果应是超时，而不是一段空的成功。模型应说系统这次没有返回进度。不说「这类申请一般三个工作日，应该快了」。天数也许出现在别的手册句子里，它不是这张保单的状态。

若客户接着问「意外医疗赔不赔牙科」，这不是进度工具的工作。硬查一次状态，回答的仍是在等收据，没有回答牙科。条款走资料：可以是 RAG，也可以是另一个只读的条款工具。两个工具可以出现在同一段对话里，不能互相代替。进度接口不负责解释保单，条款片段也不负责报告这单走到哪。

写入要再分开。客户说「帮我把缺的材料记一笔」时，那是另一个工具，带申请号作为幂等键，并且柜员确认之后才执行。读进度的描述里已经写了不修改。确认步骤放在程序里，不放在「请模型小心」里。

模型如果没发调用，却直接说「已经是待补材料」，这句不能出柜面。应用可以规定：涉及进度的最终回答必须对应一次成功的 `get_claim_status`，句子里的状态、编号和日期都要能在那次返回里找到。对不上就退回，让模型根据工具结果重写，或者明确说这次没查到。这是产品规则，不是把温度调低。

### 谁可以做什么

| 谁 | 做法 | 为什么 |
|----|------|--------|
| 普通用户 | 要今天的状态时，看产品有没有表明它查过某个来源 | 句子顺，只说明生成完成了 |
| 普通用户 | 追问返回的字段或原话，而不只追问结论 | 把「我查过」变成一次可核对的结果 |
| 普通用户 | 比金额、算日期时，要求给出算式，或使用计算器一类工具 | 多步算术不该靠语言抽样 |
| 普通用户 | 不把生产密码、完整证件号交给来路不明的插件 | 工具的权限等于这段对话能碰到的权限 |
| 开发者 | 描述里写清何时用、参数含义、禁止场景 | 模型按这段文字选择，不按你没写下来的约定 |
| 开发者 | Schema 管类型；服务端管存在性、归属和权限 | 合法的 JSON 仍可以指向别人的保单 |
| 开发者 | 读和写分成两个工具；写入要幂等键，必要时人工确认 | 重试和并行会把一次操作做成两次 |
| 开发者 | 超时和错误原文交回，日志记下名字、参数、耗时 | 失败被说成成功时，事后无法区分该查接口还是该查提示 |

普通用户改不了供应商的协议，但可以拒绝把没有出处的状态当成已经查过。开发者改得了的是边界：哪些工具存在、谁的凭证在跑、失败时对话里留下什么。提示词里加一句「不要编造工具结果」有用，它替代不了「没有调用就不许出现状态字段」这种应用层规则。

和幻觉的关系可以直接说。本系列的 [AI 幻觉（Hallucination）](AI幻觉(Hallucination).md) 把函数调用替代记忆列在缓解手段里。替代的是记忆，不是核对。工具调错、结果被忽略、或者根本没调，回答仍会像一份进度说明。先看对话里有没有这次调用和它的返回，再看句子是否只用了返回里的字段。

## 五、一句话总结

> **工具调用是让模型开口前先动手查或算，不是让它变得什么都记得。** 编排靠模型，真相靠工具。工具失败时要暴露失败，不要用流畅的中文把失败盖过去。
