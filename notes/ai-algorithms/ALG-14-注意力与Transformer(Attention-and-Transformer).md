# 注意力与 Transformer（Attention / Transformer）：让每个词直接去看和它相关的词

**ALG-14** · **2026-11-21** · **分类** 神经网络（序列，大语言模型的底座） · **难度** 中等偏上 · **面试频率** 高：FDE 岗位天天碰大模型，面试官常要你讲清注意力在做什么、为什么长文本贵；手推多头注意力的维度较少见

## 招聘切入

面试官问 Transformer，想听的不是「Query、Key、Value」背口诀，而是：**为什么模型能把相隔很远的两句话联系起来，以及这件事在上线时要付什么代价。**

这一篇练三件事：**说得清注意力在算什么、说得清为什么上下文越长越慢越贵、说得清这对客户项目里的切块、成本和延迟意味着什么。**

FDE 现场常见的是客户想让大模型读合约、保单、客服记录。甲方企业内部（银行保险、公营柜面）会追问长文件放不放得下、资料会不会送出去；AI 原生 / 产品公司更关心延迟和成本怎么控。

## 适用场景

- 理解为什么大语言模型能读上下文、能按前文回答
- 向客户解释「上下文窗口」「token 成本」「为什么要切块检索」
- 判断一个任务是否依赖远距离的前后关系（长合约里前面的定义影响后面的条款）

## 不适用场景

- 小型表格数据（保单字段、交易记录）：梯度提升等表格方法更省、更稳
- 只需要固定规则的匹配：规则或正则更便宜、可解释
- 要求每个结论都有可逐步复核的数学依据：注意力权重不等于完整解释

## 场景

一间香港虚拟保险公司，想让模型读一份几十页的条款，回答「等候期多长」。旧办法是一个词一个词按顺序读，读到后面容易忘掉前面。Transformer 的做法是：每个词都去「看」整段话里所有的词，按相关程度分配关注，再汇总。「等候期」这个词会重点看到条款里写着天数的那一句，不管它隔了多远。

## 概念

一句话：**注意力让序列里每个位置，按和其他位置的相关程度，给它们加权后取平均，Transformer 把很多层这样的注意力叠起来。**

**Query、Key、Value。** 每个词先被变成三组数字：Query 是「我在找什么」，Key 是「我有什么特征」，Value 是「我要贡献的内容」。一个词的 Query 和所有词的 Key 比较相似度，得到一组分数：

$$\text{Attention}(Q,K,V)=\text{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V$$

softmax 把分数变成加起来为 1 的权重；除以 \( \sqrt{d_k} \) 是为了不让分数太大。再用权重对 Value 加权求和，就是这个词新的表示。

**多头。** 同时做好几组注意力，每组可以关注不同关系（谁修饰谁、哪个数字对应哪个条款），最后拼起来。

**位置信息。** 注意力本身不知道词的顺序，所以要额外加入位置编码，告诉模型谁在前谁在后。

**整体结构。** 注意力层加一个前馈层，外加残差连接和归一化，叠很多层。生成文字的大模型每次只准看左边已写出的词，一个一个往后预测下一个词。

**代价。** 每个词都要和所有词比较，计算量大致随长度的平方增长：长度翻倍，注意力部分约变成四倍。所以上下文越长越慢越贵，也因此实际项目常先检索出相关片段，再交给模型。

**容易踩的事。** 第一，上下文窗口够大不等于都读得好，很长的材料中间部分容易被忽略，要实测。第二，模型会流畅地编造，答案要能指回原文出处。第三，把客户资料放进提示词前要确认是否允许出境、是否会被保留。第四，成本按 token 计，长文件反复送入会很快累积。

## 香港落地例子

虚拟保险公司的条款问答。下面的数字都是教学示意，不是任何机构的数据。

- 做法 A：整份 60 页条款每次全塞进去，平均回答约 12 秒，每次成本约为做法 B 的 8 倍
- 做法 B：先按章节切块、检索最相关的 5 段，再交给模型，平均约 3 秒
- 在 50 道人工写好标准答案的题上：A 答对约 80%，B 约 86%（检索把无关内容挡掉了）
- 要求每个答案附上条款页码，答不到就说「找不到依据」，转人工

怎么交给业务：

- 先和业务一起列出常问的 30 到 50 道题，写下标准答案和出处，做评估集
- 同时给准确率、延迟和每次的成本
- 不确定或找不到依据时转人工，并抽样复查
- 说清楚资料放在哪里、是否送出环境

同一个想法，换一类雇主，侧重不同：

| 雇主类型 | 为什么会碰到 | 你该怎么用 | 不该怎么用 |
|----------|--------------|------------|------------|
| 甲方企业内部（银行保险、公营柜面） | 长文件问答、客服辅助 | 先确认资料可否出境，答案附出处，人工复核 | 把整份客户档案直接贴进外部服务 |
| AI 原生 / 产品公司 | 产品核心就是大模型功能 | 控制上下文长度、缓存、评估延迟与成本 | 只看演示效果，不测长文本的表现 |
| 大厂云与平台 | 客户在云上调用大模型 | 讲清 token 计费、上下文上限和限流 | 承诺「想放多长都行」 |
| 咨询与系统集成 | 客户要一个「读文件的 AI」 | 用客户真实文件做小范围试点和评估集 | 用精挑的短文档做验收演示 |

## 面试怎么说

面对保险公司内部 FDE 岗的面试官，大约可以说：

> “Attention lets every token look at every other token and decide how much each one matters. Each token produces a query, a key and a value; the query is compared with all the keys, a softmax turns the scores into weights, and the output is a weighted sum of the values. A Transformer stacks many such layers, with several heads so different layers of relationship can be captured at once. The catch is cost: comparing every token with every other one grows roughly with the square of the length, so long documents are slow and expensive. In a real project I would retrieve the relevant clauses first instead of sending the whole policy, require every answer to cite its source, build a small evaluation set with the business, and route low-confidence cases to a human.”

现场用客户习惯的语言（粤语或普通话）讲清楚「每个词去看相关的词；长文件贵，所以先检索再回答，答案要有出处」；评估集、成本和资料处理方式，用英文写进确认邮件或方案。

## 小练习

下面三件事，各是依赖注意力的长距离关系、不依赖，还是要换办法？各用一句话说出理由。

1. 保单条款里第 3 页定义了「受保人」，第 40 页的除外条款引用了它，要让模型答对
2. 预测客户下月是否退保，数据是二十几个表格字段
3. 要求回答每次延迟低于 1 秒，但每次都带入 100 页文件

### 小练习

1. **依赖。** 这是远距离的指代关系，注意力正适合让除外条款直接看到前面的定义，但仍要用评估集验证。
2. **不依赖。** 表格字段没有序列关系，先用梯度提升或逻辑回归。
3. **要换办法。** 每次带入 100 页很难做到低延迟，应先检索相关片段、缩短上下文，必要时缓存。

### 自测 1

Query 表示这个词在找什么，Key 表示每个词有什么特征，两者比较得出相关程度，经 softmax 变成权重；Value 是实际贡献的内容，按权重加权求和。每个词都要和所有词比较，计算量约随长度的平方增长，所以越长越慢越贵。答到「Q 与 K 比相似度、权重加权 V、长度平方增长」即算完整。

### 自测 2

先问合规：政策文件能否放到外部模型，数据是否出境、是否被保留。再问评估：常见问题有哪些、错答的后果。设计：把政策文件切块并检索相关段落，再交给模型，答案附出处，找不到依据就转人工；用真实问题建评估集，记录延迟和成本，上线后抽样复查。答到「合规 + 检索切块 + 出处 + 人工兜底 + 评估」即算完整。
