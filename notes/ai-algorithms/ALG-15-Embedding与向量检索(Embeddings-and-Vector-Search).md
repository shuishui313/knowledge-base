# Embedding 与向量检索（Embeddings and Vector Search）：把意思变成坐标，再找最近的

**ALG-15** · **2026-11-25** · **分类** 表示学习 / 检索（大语言模型落地） · **难度** 中等 · **面试频率** 高：做大模型落地的 FDE 面试几乎绕不开，常问 embedding 是什么、怎么比相似度、为什么检索会找错；手写近似最近邻索引少见

## 招聘切入

面试官问「embedding 和向量库」，想听的不是「把文字变成向量」这一句，而是：**为什么意思相近的句子会靠在一起，怎么找最近的，以及它在哪些情况下会找错。**

这一篇练三件事：**说得清 embedding 是什么、说得清相似度怎么算和怎么快速找、说得清上线后怎么发现它找错了。**

FDE 现场常见的是客户说「我们有一堆文件，想让人用自然语言查」。甲方企业内部（银行保险、公营柜面）会追问资料放在哪、会不会出境；AI 原生 / 产品公司更关心延迟、成本和召回质量。

## 适用场景

- 用户的说法和文件的写法不一样，关键词搜不到（问「退保要等多久」，文件写「终止保单的处理时间」）
- 找相似案例、相似投诉、重复工单
- 给 RAG 做第一步检索（下一篇再讲怎么把检索结果交给大模型）

## 不适用场景

- 要精确匹配的字段：保单号、人名、金额、条款编号，用数据库查询或关键词更稳
- 文件很少（几十条），直接全文放进提示词或人工归类更省事
- 要求能逐条解释「为什么这条排第一」：相似度分数只说明接近，不说明理由

## 场景

一间香港虚拟银行的客服知识库，有几百条 FAQ。客户问「转数快转错数怎么办」，FAQ 标题写的是「误转款项的处理」，两句话几乎没有相同的词。关键词搜索会漏掉它。用 embedding：把每条 FAQ 和这句问题都变成一串数字，意思相近的排得近，直接找最近的几条。

## 概念

一句话：**embedding 把一段文字映射成一个定长的向量，意思相近的文字向量也相近；向量检索就是在大量向量里，找离问题向量最近的几个。**

**embedding 模型。** 它是事先训练好的神经网络（和 ALG-14 的 Transformer 同源），输入一段文字，输出比如几百到上千个数字。训练目标是让意思相近的文字更近、不相关的更远。你在项目里通常直接调用现成模型，不自己训练。

**怎么比近。** 最常用的是余弦相似度，看两个向量夹角有多小：

$$\cos(a,b)=\frac{a\cdot b}{\lVert a\rVert\,\lVert b\rVert}$$

越接近 1 越相近。很多模型输出的向量已经归一化，这时点积和余弦等价。K 近邻（ALG-04）的「找最像的几个」，在这里就是在向量空间里做。

**怎么快速找。** 逐条比对，条目有几百万时太慢。向量库用近似最近邻（ANN）索引，比如 HNSW、IVF 这类，用少量精度换很大的速度：偶尔会漏掉真正最近的那条。

**切块。** 长文件不能整份变成一个向量，否则意思被冲淡。通常先切成一段一段（按章节或几百字），每段一个向量，检索时返回段落。

**会在哪里坏。**

- 第一，换了 embedding 模型，旧向量要全部重新生成，两个模型的向量不能混着比
- 第二，模型对粤语口语、繁体与英文夹杂、行内缩写的效果不一定好，要用客户真实的问法实测
- 第三，数字、否定和细节容易被抹平：「可以退保」和「不可以退保」可能很近
- 第四，切块太大意思被冲淡，太小又丢上下文
- 第五，向量里仍可能含个人信息，客户资料送去外部服务生成向量前要确认合规
- 第六，近似索引会漏，权限也要跟着文件走，不能让没权限的人检索到别人的资料

## 香港落地例子

虚拟银行客服 FAQ 检索。下面的数字都是教学示意，不是任何机构的数据。

- 做法 A：关键词搜索 FAQ 标题与正文
- 做法 B：embedding 检索，返回最相近的 3 条
- 做法 C：B 再加关键词条件（产品名、业务类别）一起过滤
- 在 60 条人工整理的真实问法上，看「正确 FAQ 是否在前 3 条」：A 约 55%，B 约 80%，C 约 88%（数字仅为示意）
- 失败案例单独列出来：否定句、含产品名缩写、粤语口语写法，逐条看原因

怎么交给业务：

- 和业务一起整理 50 到 100 条真实问法，每条标出该命中的 FAQ，做评估集
- 指标先看「前几条里有没有正确答案」，不要只看分数高低
- 约定找不到够近的条目时（相似度低于阈值）不硬给，转人工，阈值用评估集定
- 说清楚资料和向量存在哪里，谁能检索到什么

同一个想法，换一类雇主，侧重不同：

| 雇主类型 | 为什么会碰到 | 你该怎么用 | 不该怎么用 |
|----------|--------------|------------|------------|
| 甲方企业内部（银行保险、公营柜面） | 内部知识库、柜面问答 | 先确认资料能否出境，按权限过滤，附出处 | 把全部客户档案向量化后让所有人检索 |
| AI 原生 / 产品公司 | 检索是产品的底层能力 | 评估召回，混合关键词，控制延迟与成本 | 只凭几个演示问题就定模型 |
| 大厂云与平台 | 客户用平台自带的向量服务 | 讲清维度、索引类型和换模型要重建 | 承诺「语义搜索一定找得准」 |
| 咨询与系统集成 | 客户要一个「智能搜索」 | 用客户真实问法做小评估集，再定方案 | 用精挑的容易问题做验收 |

## 面试怎么说

面对虚拟银行内部 FDE 岗的面试官，大约可以说：

> “An embedding model turns a piece of text into a vector, so that texts with similar meaning end up close together. I would embed each FAQ chunk once, embed the customer's question at query time, and return the nearest chunks by cosine similarity. For millions of items we use an approximate nearest neighbour index, which trades a little recall for speed. It is strong when users and documents use different words, but weak on exact identifiers, negations and domain abbreviations, so I would combine it with keyword filters. Before going live I would build an evaluation set from real questions with the business, measure whether the right answer appears in the top three, set a threshold below which we hand over to a human, and confirm where the data and vectors are stored.”

现场用客户习惯的语言（粤语或普通话）讲清楚「意思相近的排得近，找最近的几条；精确字段要配关键词；找不到就转人工」；评估集、阈值和数据存放位置，用英文写进确认邮件或方案。

## 小练习

下面三件事，用 embedding 检索合适吗？各用一句话说出理由。

1. 客户输入保单号 P-883201，要查这张保单
2. 同事想找「和这条投诉说法不同但意思相同」的历史投诉
3. 换了新的 embedding 模型，想直接把新旧向量放在同一个库里一起查

### 小练习

1. **不合适。** 保单号是精确字段，用数据库按号查，又准又快，向量检索可能找出相似但错误的号码。
2. **合适。** 说法不同、意思相同，正是 embedding 擅长的，但仍要用评估集抽查。
3. **不行。** 不同模型的向量空间不同，不能混着比；换模型要把所有文件重新生成向量。

### 自测 1

embedding 是把文字映射成一个定长向量，意思相近的文字向量更近。精确逐条比对在数据量大时太慢，近似索引用少量召回换大幅提速，可以通过调参数、混合关键词和评估集把漏掉的比例控制在可接受范围。答到「向量表示意思、相似度找最近、近似换速度、要评估」即算完整。

### 自测 2

先问：运单说明里有没有个人资料、能否出外部服务、是否要按分公司权限过滤；常见问法有哪些，是中文、英文还是夹杂；找错的后果有多大。设计：按条或按段切块，生成向量；运单号、日期、网点等精确字段用结构化过滤，说明文字用向量检索，两者合并；返回原文和单号作为出处，相似度过低就转人工；用真实问法建评估集，看前几条命中率，并记录延迟和成本。答到「精确字段 + 语义检索 + 权限与合规 + 出处与兜底 + 评估」即算完整。
