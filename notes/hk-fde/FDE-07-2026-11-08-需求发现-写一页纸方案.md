# 写一页纸方案：让所有人签同一个版本

**FDE-07** · **2026-11-08** · Day 7 · **主题板块** 需求发现 · **难度** 入门

## 场景：开完三次会，大家记得的不一样
一家香港物业管理公司，管着 40 多个屋苑。住户报修全靠 WhatsApp 和电话，客服每天手动把讯息转给维修部，漏单、重复派工是常态。

你做完 discovery（第 4 课），排好了优先级（第 6 课）：第一期只做「报修讯息自动分类 + 派单建议」，不做住户聊天机器人。

开完会大家都点头。两周后：

- 营运经理以为「派单」是全自动的
- IT 以为你会自己接他们的工单系统，没给你开权限
- 法务第一次听说住户讯息要送去 LLM 处理

没人说谎，只是三个人在三个会议里，听到了三个版本。**这时候缺的不是更好的模型，是一张大家签过名的纸。**


## 类比：你在微博写过的技术方案
微博要上一个新的 feed 缓存方案前，你们大概会写一份设计文档，然后开评审会：为什么要改、改成什么样、容量估算、回滚方案、谁配合。

写这份文档，真正的作用不是「记录」，而是**逼所有人在动手前对齐，把分歧提前暴露在纸上**，而不是暴露在线上故障里。

One-pager 就是给客户看的那份设计文档。只是读者从工程师换成了营运经理、IT 和法务，所以要更短、更少术语，而且多了一栏：**客户要做什么**。

另一个角度：它像一份 API 契约。先把 request/response 定下来，双方才能并行开发；one-pager 先把「交什么、怎样算交了、你给我什么」定下来，双方才能各自推进。


## 原理

### 它解决什么问题
把 discovery、scope、优先级三课的结论，压成**一页可以签字的共识**：让不在场的人也能看懂，让说过的话有据可查。

### 怎么工作：一页纸的 8 个栏目
```
1. 问题与现状     现在怎么做、痛在哪、baseline 数字（第4课）
2. 目标与指标     做完后哪个数字变成多少（第5课的验收标准）
3. 方案一张图     数据从哪来 → 经过什么 → 到谁手里
4. 范围           第一期做什么 / 明确不做什么（第6课的「不」）
5. 假设与风险     数据质量、准确率不确定、合规（PDPO）
6. 客户要提供的   谁、给什么、哪天前给（权限、样本数据、对接人）
7. 时间线         2–4 个里程碑，每个有出口标准（第2课）
8. 需要的决定     请谁在哪天前拍板什么
```

拿物业的例子，第 3 栏可以就是一行：
```
住户 WhatsApp → 分类模型（类别+紧急度+置信度）
   → 置信度高：建议派单，客服一键确认
   → 置信度低：进人工队列
   → 结果写回工单系统
```
注意「客服一键确认」：这一句就把营运经理以为的「全自动」改正了。

### 关键取舍
- **一页 vs 完整**：写不完的细节放附录，正文只放会影响决定的东西。读者是忙的经理，第一屏看不懂就不会往下看。
- **具体 vs 灵活**：数字写死（「派单建议准确率 ≥ 85%，低于 70% 置信度转人工」）会让你被追责，但写得模糊等于没写。宁可写具体，再在第 5 栏写清假设。
- **写给谁**：同一份纸要让营运看懂价值、IT 看懂对接、法务看懂数据流。所以方案图里要写清数据去哪里，而不是用了哪个模型。

### 会在哪里坏
- **第 6 栏空着**：客户的权限、数据、对接人一拖，你的时间线全部顺延，最后还是 FDE 背锅。
- **没有 baseline**：上线后说「快了很多」，但没有之前的数字，sponsor 拿不出东西汇报。
- **写完不签**：发了邮件没人回，等于没有共识。要约一个 30 分钟会，当场过一遍，确认谁同意。
- **不更新版本**：scope 变了 one-pager 没变，两份「真相」并存。每次改动写版本号和改了什么。


## FDE 视角
- **怎么用**：discovery 结束一周内发出初稿，最好在 workshop 当天就用白板版本跟客户一起填。客户参与写的，他们才会认。
- **客户常问**：「可唔可以唔写咁死？」可以把数字写成区间，或者写「第 3 周用真实数据测完再定」，但不要拿掉。没有数字，第 8 周就没法说做成了没有。
- **另一个用途**：它也是内部文档。你的销售、产品团队靠它知道这个客户承诺了什么，哪些需求该回流到产品（第 1 课）。
- **常见坑**：
  - 写成技术方案，满篇 embedding、vector DB，营运经理看不下去
  - 只发给 sponsor，IT 和法务第一次看到时已经是上线前
  - 把 one-pager 当合同用。它是共识，不是法律文件；商务条款交给 SOW


## 面试怎么问
**题目**：「Discovery 做完了，你要给客户写一份方案。你会放哪些内容？怎么确保客户真的同意了？」

**答题思路**：先说结构（问题与 baseline → 指标 → 方案图 → 范围与不做 → 假设风险 → 客户要提供什么 → 里程碑 → 需要的决定），重点讲「客户要提供什么」和「当面过一遍、拿到确认」这两步，再拿微博评审设计文档的习惯说明你本来就这样做事。


## 一句话带走
**One-pager 是写给客户看的设计文档：把问题、指标、范围和「你要给我什么」压成一页，让所有人在动手前签同一个版本。**

## 自测

1. 如果 one-pager 里写了漂亮的方案和指标，但没写「客户要提供什么、哪天前提供」，项目中途最可能出什么事？为什么这一栏有时比方案本身还重要？
2. 如果你在咨询与系统集成公司做 FDE，客户已经和你们签了 SOW，还需要再写一份 one-pager 吗？两者分工是什么？
